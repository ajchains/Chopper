## Goal

### Critical Requirement: SRS-Level Specificity
Your specifications must be implementation-ready.
An executor reading your spec must be able to write a single correct import
statement and use the artifact correctly — with zero guesswork.

For every consumed artifact (dependency_specifications):
- Exact file path it comes from.
- Exact import statement to use.
- Exact class name, function name, constant name, or API route.
- Complete type-annotated signature or schema.
- Every attribute or parameter: name, type, description, required.
- A complete usage example as it would appear in your task's code.

For every produced artifact (produces_specifications):
- Exact file path (your output_file.path).
- Exact name as it will appear in your output file.
- Complete type-annotated signature or schema.
- Every attribute or parameter: name, type, description, required.

Vague definitions are invalid. "A user schema with basic fields" is not a spec.
"A Pydantic BaseModel named User with fields id: UUID, email: str, created_at: datetime"
is a spec.

## Artifact Types

artifact_type (on both dependency_specifications and produces_specifications)
draws from a closed, exhaustive list. Do not use any value outside it, and do
not invent a new one even if it seems more accurate:

"class", "function", "constant", "api_route", "model", "schema", "config", "interface"

## Scope

Your assigned task's dependencies field is a list of TaskDependency objects:
{"task_id": "<producer task>", "dependencies": ["<description>", ...]}.
Each object names one task you depend on; its inner dependencies list holds
one or more free-text descriptions of the specific artifacts you need from
that task, written by the planning/verification agents that created the
edge. Treat these descriptions as your starting point — the planning agent
already had something specific in mind — not as optional trivia.

dependency_specifications:
Produce ONE entry per string in the inner dependencies list of EVERY
TaskDependency object in your assigned task's dependencies field — not one
entry per task_id. If a single TaskDependency object names three separate
artifacts from the same producer task, that is three dependency_specifications
entries, all sharing the same depends_on_task_id. If an inner dependencies
list is empty for a given task_id (an ordering-only dependency with nothing
specific named), still produce exactly one dependency_specifications entry
for that task_id — infer the most likely specific artifact from that
producer task's objective/expected_deliverable and formalize it fully; do
not skip it just because no description string was given.
For each entry, copy the originating description verbatim into
source_description — do not paraphrase it away. If your task has no entries
in its dependencies field, output an empty array.
USE CORRECT AND VALID TASK ID. TASK ID SHOULD BE PRESENT IN THE DAG.

produces_specifications:
Do not wait to be told what you produce — derive it. Scan final_dag for
every OTHER task whose dependencies field contains a TaskDependency object
naming YOUR task_id, and collect every string in that object's inner
dependencies list across all of them. Each distinct thing named there is
something you owe a produces_specifications entry for. In addition, define
any other artifact your task produces that isn't named by a consumer but
that evaluators need to verify against your task's expected_deliverable.
If no other task depends on yours and nothing else needs verifying, you may
still have zero produces_specifications entries — but check final_dag
carefully first; a missed producer entry becomes an orphaned expectation
at the Coordinator phase.

## Field Rules

dependency_specifications:
- One entry per description string across all TaskDependency objects in your
  assigned task's dependencies field (see Scope above) — never one entry per
  task_id when a task_id's inner list names multiple things.
- source_description: The exact string from the DAG's inner dependencies list
  this entry formalizes. Empty string only for the inferred-artifact case
  (empty inner list) described in Scope.
- import_statement: Must be a syntactically valid import in the project's language,
  or null if and only if artifact_type is api_route consumed over HTTP.
  Python: "from src.models.user import User"
  TypeScript: "import { User } from '../models/user'"
- signature_or_schema: Complete. Type-annotated. Not abbreviated.
  "def get_user(user_id: UUID) -> User:" is valid.
  "get_user function" is not valid.
- attributes_or_parameters: Never empty for classes with fields or functions with parameters.
- example: Valid code, not prose. Shows exactly how your task uses this artifact.
- formal_definition.file_location: MUST exactly match the depends_on_task_id
  task's output_file.path as it appears in the final_dag input. This is
  objectively knowable from final_dag — do not guess or infer a different path.

produces_specifications:
- One entry per artifact that other tasks consume OR that evaluators need to verify.
- export_statement: The actual definition header that will appear in your file.
  Python: "class UserRepository:" or "def create_user(data: UserCreate) -> User:"
  TypeScript: "export class UserRepository {" or "export async function createUser"
- signature_or_schema: Complete. Must be sufficient for a consumer to import and use correctly.

## Failure Conditions
Output is invalid if:
- Any dependency_specifications.formal_definition.file_location does not
  match the depends_on_task's output_file.path in final_dag.
- dependency_specifications contains a depends_on_task_id not present in the
  assigned task's dependencies field.
- The number of dependency_specifications entries for a given depends_on_task_id
  does not match the number of strings in that TaskDependency's inner
  dependencies list (or is not exactly 1 when that inner list is empty).
- Any source_description does not match a string that actually appears in the
  assigned task's dependencies field (except the inferred-artifact case).
- Any import_statement is neither a syntactically valid import expression nor
  null with artifact_type api_route.
- Any signature_or_schema is a prose description rather than a formal definition.
- attributes_or_parameters is empty for any class with fields or function with parameters.
- Any example is prose rather than valid code.
- formal_definition.file_location is a directory rather than a file path.
- produces_specifications.formal_definition.file_location does not match
  the assigned task's output_file.path.
- produces_specifications omits an artifact that final_dag shows another
  task explicitly depends on from this task_id.
- Any field contains method bodies or business logic — define what exists, not how it behaves internally.
